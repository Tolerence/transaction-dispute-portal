# 1. Docker Compose for the local stack

Status: accepted

## Context
The portal has four moving parts: PostgreSQL, the Spring Boot API, the nginx-served web app, and (for SSO testing) Keycloak. A developer or reviewer should be able to run the whole system with one command, on a laptop, without installing Java, Node or Postgres globally.

## Decision
Use Docker Compose (`docker-compose.yml`, plus `docker-compose.sso.yml` for Keycloak) to run the stack. Optional monitoring is a separate Compose profile (see ADR 2).

## Consequences
- `make up` builds the jars and web bundle on the host, then packages them into images. Docker images contain no build tools, which keeps them small and keeps the build on the host's trusted network.
- Compose is not an orchestrator. There is no scheduling across machines, no rolling deploys and no self-healing beyond `restart`. Production deployment is out of scope for this repository and would need a platform such as Kubernetes or a managed container service.
- Services set memory limits (`mem_limit`) so a runaway container cannot starve the others on a developer machine. These are not production capacity plans.
- Secrets come from `.env`, which is generated by `make env` and gitignored. Production must inject secrets from its own secret store.

## Alternatives considered
- **Kubernetes (kind or minikube locally):** closer to production, but heavy for a laptop and adds a learning cost that does not help the portal's domain logic.
- **Running each component by hand:** fast for one developer, but every reviewer would have to reproduce the setup.
